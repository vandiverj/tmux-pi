# Pi mechanics

Use `dispatch_role`, `task_index`, and `task_collect` for ordinary orchestration. They call the shared repository command `tp-agent`. Use `bash` for `tp-agent inspect ID`, `tp-agent message ID --text TEXT`, `tp-agent stop ID`, `tp-agent review ID` (an independent reviewer on another provider) and `tp-agent retry ID --reason TEXT --escalate` when needed; `dispatch_role` chooses the model itself unless you pass one. Older subagent tools remain available for existing sessions but do not record a role. The tmux status pane and viewer show the same tasks.

A failing test a worker reports as pre-existing or unrelated is a claim to check, not a reason to move on. Before you commit the slice that reported it, run `tp-agent dispatch --investigate-failure ID` (collect shows the worker's `FAILING_TESTS:` block) unless an investigation of that test is already open.

Run `task_index` at session start and after compaction; nothing notifies you when a worker changes state, so check it before reporting on running work. After compaction, if a workspace is attached, run `tp-agent work recover` (through `bash`) whether or not `task_index` shows a pending recovery (Pi sets no marker), re-verify any "done" claim against live records, and tell the user each open decision it lists.

`tp-agent context --task TEXT [--workdir DIR]` (through `bash`) suggests `context` specs for a task. They are suggestions: prefer a file you already know is right, and `tp-spawn` still caps and screens each one.

Lanes: for two or more substantial streams of work that change different paths at once, give each a lane (a git worktree and branch) with `tp-agent dispatch --lane NAME --step ID --role ROLE --task TEXT` through `bash` (a new lane also takes `--domain TEXT --touches PATH...`). Never start a worker by hand in a lane's worktree: a lane takes one writer at a time and only `--lane` knows it. Use `--tests affected` in a lane. `tp-agent lanes` shows each lane's `waiting_on`: `worker` (wait, collect, or answer it); `review` (one is running, or start it with `tp-agent review AUTHOR --force`); `orchestrator-dispatch` (dispatch the next task, or `tp-agent retry` after a rejection); `orchestrator-commit` (commit the approved work in the lane's worktree); `orchestrator-close` (`tp-agent lane close NAME STEP`; the next step cannot start before); `none` (the lane takes no more work). A refusal names the command that clears it; `docs/lanes.md` has the table. Lanes are merged by hand for now: merge each into the integration branch yourself, then run the whole test suite once from the main checkout.
